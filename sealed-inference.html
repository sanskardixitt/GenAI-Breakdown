What “private” actually has to mean

Almost every “we self-host our LLM, so our data is private” claim is false on inspection. The model weights running on your own GPU are the easy part. Privacy is decided by the other nine or ten network paths that a normal inference stack opens by default.

Start by writing the requirement down as something testable, because “private” is not. A workable definition has four clauses:

  1. No third party ever receives the content. Prompts, retrieved documents, embeddings, and completions are processed only by compute you control, inside accounts you own.
  2. No content is used for training by anyone, including AWS, including implicitly through “abuse detection” or “service improvement” sampling.
  3. Content stays inside a declared geographic and legal boundary — a named AWS Region, under a named legal entity, with a named encryption key you can revoke.
  4. You can prove clauses 1–3 from logs without trusting anybody’s word, including your own engineers’.

Clause 4 is what separates a real design from a slide. A control you cannot evidence is a control you do not have.

The seven layers that have to hold

Defence-in-depth here is not a slogan, it is an ordering. Each layer catches what the layer above it missed, and each is independently auditable.

  1. 01OrganizationService Control Policies deny whole categories of action across every account — unapproved Regions, creating an internet gateway, stopping CloudTrail, weakening S3 Block Public Access. An SCP cannot be overridden by a local admin, which is the point.
  2. 02AccountBlast-radius separation. Inference, data, network, shared services, security tooling and log archive are separate AWS accounts, so a credential compromise in one does not reach the corpus in another.
  3. 03NetworkA VPC with no internet gateway, no NAT gateway and no public IPs. Every AWS API call leaves through an interface VPC endpoint whose policy pins the calling principal to your organization.
  4. 04IdentityIAM roles only, no long-lived keys. EKS Pod Identity or IRSA for workloads, GitHub OIDC federation for CI, permission boundaries so that even an over-broad role cannot escape the guardrail.
  5. 05CryptographyCustomer-managed KMS keys on S3, EBS, EFS, FSx, Aurora, OpenSearch, ECR and CloudWatch Logs. The key policy is the last line of defence: revoke it and every copy of the corpus becomes ciphertext.
  6. 06ApplicationTenant isolation in the retriever, guardrails on input and output, prompt/response redaction before anything is logged, and strict allow-lists for agent tool calls.
  7. 07EvidenceOrganization-wide CloudTrail with data events, VPC Flow Logs, AWS Config conformance packs and a write-once log archive. This layer does not prevent anything; it is what turns the other six from assertions into findings.

The load-bearing idea

Privacy is an egress property, not a hosting property. Ask of every component: “what DNS names can this resolve, and what IPs can it reach?” If the honest answer is “anything”, the workload is not private no matter whose GPUs it runs on.

The honest tradeoff

Self-hosting gives you a technical boundary you can inspect. Bedrock gives you a contractual and architectural boundary you must accept on evidence — and its evidence is strong: in-Region processing, no storage of inputs or outputs for base models, and no use of your content to train them. Many teams choose self-hosting for reasons that are really about procurement and auditor comfort, then quietly leak more data through an unpinned pip index than Bedrock ever would have seen. Pick the boundary you can actually operate.

The request lifecycle, hop by hop

Thirteen hops from keystroke to token. At every one of them there is a specific reason the content cannot leave — and it is never “because we told the model not to”.

The other two paths

ASYNC / BATCH

S3 → SQS → worker → S3

Bulk summarisation and classification do not belong on the synchronous path. Land the input in S3, fan out through SQS with a dead-letter queue, run the same vLLM fleet at high batch size with no latency SLO, and write results back to a KMS-encrypted prefix. This is where Spot instances and Inferentia earn their keep, and where you can drive GPU utilisation above 80 %.

AGENTIC / TOOL-CALLING

The threat surface multiplies

The moment the model can call tools, a prompt-injected instruction inside a retrieved document becomes a request your own credentials will execute. Tools get an explicit allow-list, their own least-privilege IAM role (never the orchestrator’s), a human approval gate for anything that writes, and a hard cap on loop iterations and total tokens. Treat every tool result as untrusted input and re-run the input guardrail on it.

Sealing the network

Three mechanisms, applied together, in this order: remove the route, pin the door, and blind the resolver. Any two of the three still leaves a hole.

1 · Remove the route

The inference and data subnets have route tables containing exactly two kinds of entry: the VPC-local route, and prefix-list routes to the Transit Gateway for corporate CIDRs. There is no 0.0.0.0/0. No internet gateway exists in the VPC; no NAT gateway exists in the VPC; MapPublicIpOnLaunch is false everywhere. This is not a firewall rule that can be edited — there is simply no path, and creating one is denied at the organization level.

2 · Pin the door

With no route out, every AWS API call has to traverse an interface VPC endpoint — a PrivateLink ENI inside your own subnet, addressed with a private IP, reached over the AWS backbone rather than the internet. Enable private DNS on each so that the SDK’s default hostname (s3.eu-central-1.amazonaws.com) resolves to the ENI and no application code has to change.

Then constrain the endpoint itself. An endpoint policy is the choke point that stops the classic exfiltration move: valid credentials writing your corpus into somebody else’s S3 bucket.

3 · Blind the resolver

DNS is the egress channel people forget. Even with no IP route, a resolver that will answer for a1b2c3.exfil.example.com lets a compromised process encode data into subdomain labels and read it off the authoritative server’s query log. Route 53 Resolver DNS Firewall fixes this properly: an allow-list rule group for the handful of domains you genuinely need, then a final BLOCK rule on * at the lowest priority.

ALSO REQUIRED

IMDSv2, hop limit 1

Force HttpTokens=required and HttpPutResponseHopLimit=1 on every node. Otherwise a compromised container reaches the instance metadata service and assumes the node role, sidestepping your carefully scoped pod identity.

ALSO REQUIRED

Pod-level egress policy

Security groups are per-ENI, so on EKS they are per-node unless you use security groups for pods. Layer a Kubernetes NetworkPolicy (Calico or the VPC CNI network policy engine) so the vLLM pod can talk to the orchestrator and the endpoint CIDRs, and nothing else.

IF YOU MUST

An explicit egress tier

When some component genuinely needs the internet, do not punch a NAT into the inference VPC. Put a forward proxy or AWS Network Firewall in a separate egress VPC behind the Transit Gateway, allow-list by SNI, log every request, and never route the inference subnets through it.

How you prove it, not just claim it

Turn on VPC Flow Logs for ALL traffic, not just REJECT, deliver them to the log-archive account in Parquet, and partition by day. Then the entire zero-egress claim reduces to one query that must return no rows:

Athena — the auditor’s one-linerexpected result: 0 rows
SELECT dstaddr, dstport, SUM(bytes) AS bytes_out, COUNT(*) AS flows
FROM   vpc_flow_logs
WHERE  account_id = '111122223333'
  AND  day BETWEEN '2026/07/01' AND '2026/08/18'
  AND  flow_direction = 'egress'
  AND  action = 'ACCEPT'
  AND  NOT regexp_like(dstaddr, '^10\.')   -- VPC-local + corporate via TGW
GROUP BY dstaddr, dstport
ORDER BY bytes_out DESC;

Pair it with AWS Config rules that alarm on the existence of the things you have banned — vpc-sg-open-only-to-authorized-ports, ec2-instance-no-public-ip, s3-bucket-public-read-prohibited, plus a custom rule that fails if any route table in the account contains a 0.0.0.0/0 target of type igw- or nat-. Detective and preventive controls answer different auditor questions; you need both.

The inference plane

Where the privacy work stops and the engineering work starts. The two numbers that decide your hardware bill are model bytes and KV-cache bytes — and almost everyone underestimates the second.

Sizing the GPU: the arithmetic everyone skips

VRAM has three consumers. Weights are the obvious one and the easiest to shrink. The KV cache is the one that surprises people, because it scales with concurrency × context length, which is exactly the axis your product roadmap keeps pushing on.

KV cache per tokenthe formula worth memorising
KV_bytes_per_token = 2 (K and V) x n_layers x n_kv_heads x head_dim x dtype_bytes

Llama-3.1-70B, FP16 KV:  2 x 80 x 8 x 128 x 2  =  327,680 B  =  320 KiB / token
                                                   (8 KV heads, not 64 - GQA is
                                                    doing enormous work here)

At 8,192 tokens of context:   320 KiB x 8,192      =  2.5 GiB per sequence
At 32 concurrent sequences:   2.5 GiB x 32         =   80 GiB of KV cache alone

Total VRAM = weights + KV + activations/CUDA graphs/fragmentation (~8-12 GiB)

The serving layer is where throughput comes from. A naive model.generate() loop on the same hardware will do somewhere between a tenth and a thirtieth of what a continuous-batching server does, because it leaves the GPU idle between requests and pads every sequence to the longest in the batch.

The capacity problem nobody puts on the architecture diagram

You cannot simply launch eight p5.48xlarge instances. Large GPU capacity is constrained, per-account service quotas for accelerator vCPUs start low and take days to raise, and the honest options are ML Capacity Blocks (reserve a block of GPUs for a future window), On-Demand Capacity Reservations, or designing for the smaller, far more available g6e family. A design that assumes p5 availability and gets none is a design that does not ship. Build the fallback path into Karpenter’s NodePool as a second, cheaper instance family with a lower weight.

Autoscaling and the cold-start problem

GPU nodes take minutes to become useful: instance launch, GPU driver and device-plugin readiness, container image pull (a vLLM image with CUDA is commonly 8–15 GB), and then weight loading. Naive setups take 10–20 minutes to add a replica, which makes autoscaling decorative.

  • Scale on the right signal. GPU utilisation is a lagging, misleading metric — a memory-bound decode phase can sit at 95 % “utilisation” doing very little work. Scale on vllm:num_requests_waiting (queue depth) and observed TTFT against your SLO, via KEDA or the Kubernetes Gateway API inference extension.
  • Attack image pull. Pre-pull onto the AMI, use SOCI lazy loading for ECR, or bake a custom EKS-optimised accelerated AMI. Keep the runtime image and the weights separate so a code deploy does not re-pull 140 GB.
  • Attack weight load. FSx for Lustre linked to the weights bucket gives parallel multi-GB/s reads; Mountpoint-S3 is simpler and often enough; SageMaker’s fast model loader streams weights directly to GPU memory. Keeping an EBS snapshot of a pre-warmed volume is the crude but effective option.
  • Keep a warm floor. For an interactive product, scale-to-zero is usually the wrong goal. Hold one warm replica per AZ, autoscale above it, and use the async queue path to absorb bursts rather than making users wait for a node.
  • Route for cache hits. Prefix caching only pays if requests with the same system prompt or same conversation land on the same replica. Consistent-hash routing on a session or prefix key can be worth more than an extra GPU.

Measure the two latencies separately

TTFT (time to first token) is dominated by the prefill phase and scales with prompt length — it is a compute-bound problem, and it is what makes a chat UI feel slow. TPOT (time per output token, sometimes ITL) is the decode phase, memory-bandwidth-bound, and determines how fast text streams. Reporting a single “p95 latency” number hides which one you have broken. Benchmark with vllm bench serve, LLMPerf or GenAI-Perf against realistic prompt-length distributions, not fixed-size synthetic ones.

The private data plane

The corpus is worth more than the model. Weights are replaceable; your customers’ documents are not. Most real breaches in this architecture would be retrieval bugs, not GPU bugs.

Ingestion

The pipeline is unglamorous and it is where compliance lives: S3 landing zone with object versioning and a KMS CMK → EventBridge on object-created → Step Functions orchestrating parse (Textract for scanned PDFs, an in-VPC parser for everything else) → chunk → classify and redact (Comprehend PII detection, Macie for discovery at rest) → embed on your own GPUs → upsert into the vector store with tenant and ACL metadata → write lineage to a catalogue.

Two design rules carry most of the weight. First, the chunk carries its own access-control metadata — tenant, classification, source system, source ACL — copied at index time, so retrieval can filter without a second round trip. Second, the index is versioned and deployed blue/green, because changing the embedding model invalidates every vector you have and you cannot re-embed a hundred million chunks in place while serving traffic.

The failure mode that will actually bite you

Cross-tenant retrieval leakage. Filtering by tenant_id in application code is not isolation — it is a convention that survives until someone adds a code path that forgets. Enforce it where it cannot be forgotten: PostgreSQL row-level security bound to a session variable set from the verified JWT claim, or a separate OpenSearch index per tenant with an IAM policy that only that tenant’s role can read. Then write the test that proves it: an automated suite that authenticates as tenant A, issues queries engineered to match tenant B’s documents, and fails the build if a single B-owned chunk appears in the candidate set — checked before reranking, not after, because the reranker is not a security control.

Embeddings, rerankers and the quiet leak

Calling a hosted embedding API sends every chunk of your entire corpus to a third party — typically far more content than the chat traffic everyone worries about, and all of it at once during backfill. If the deployment is private, the embedding model must be private too. Self-host bge-m3, E5, Nomic Embed or Qwen3-Embedding on the same cluster; they are small, run happily on a g6, and batch beautifully.

The same applies to reranking. A cross-encoder such as bge-reranker-v2-m3 over the top 50 candidates typically improves answer quality more than swapping the generation model, and it costs a fraction of a GPU. If you use a managed reranker, it sees your documents.

Fine-tuning without leaking the training set

  • Prefer LoRA/QLoRA over full fine-tuning for domain adaptation: hours not weeks, one GPU node not a cluster, adapters small enough to version in ECR and hot-swap in vLLM per tenant.
  • Run SageMaker training jobs in VPC mode with EnableNetworkIsolation, output to a KMS-encrypted S3 prefix, with inter-container traffic encryption on for distributed jobs.
  • Assume the model memorises. A model fine-tuned on tenant A’s data will sometimes emit tenant A’s data. If you fine-tune per customer, you must isolate the adapters per customer — there is no prompt that undoes memorisation.
  • Right-to-erasure is a real engineering problem. Deleting a document means deleting its chunks, its vectors, its cache entries, its trace records — and if it was in a fine-tuning set, retraining. Design the deletion path on day one; it is far harder to retrofit than to build.

Security and the LLM threat model

Classic cloud security still applies in full. On top of it sits a genuinely new class of vulnerability, because for the first time the data plane and the control plane are the same string of text.

Encryption, keys and the kill switch

Use customer-managed KMS keys rather than AWS-managed ones everywhere the corpus can rest: S3, EBS volumes on the GPU nodes, EFS and FSx, Aurora, OpenSearch, ECR, Secrets Manager, and CloudWatch Logs. The reason is not stronger cryptography — both are AES-256 — it is that a CMK has a key policy you write. You control who may decrypt, you see every Decrypt call in CloudTrail, and you can disable the key. Revoking a CMK turns every copy and every backup of that data into ciphertext in one action, including copies you have lost track of.

In transit: TLS 1.2 minimum and 1.3 where you can, terminating on certificates from ACM Private CA so no public CA is involved in your internal trust chain. Inside the cluster, a service mesh or vLLM’s own TLS gives you mTLS between orchestrator and model server, which matters more than it sounds — that hop carries the fully assembled prompt including every retrieved document.

Confidential computing, honestly assessed

Every EC2 Nitro instance already runs on the Nitro System, where there is no operator SSH access to the hypervisor and no mechanism for an AWS employee to read instance memory. Nitro Enclaves go further: an isolated VM carved from the parent instance with no persistent storage, no interactive access and no external network, and cryptographic attestation so KMS will only release a key to an enclave whose measured image hash matches a value in the key policy. That is a strong story for key handling and small sensitive computations. It is a weaker story for LLM inference, because enclaves have historically not had GPU access — the practical pattern is to keep keys and decryption in the enclave and accept the Nitro System’s guarantees for the GPU itself. If you need GPU-level confidential computing, that is an H100/H200 Confidential Computing mode question, and you should verify current support before designing around it.

Guardrails on a self-hosted model

The under-known fact worth carrying into an interview: Bedrock Guardrails can be applied to a model that is not on Bedrock. The ApplyGuardrail API evaluates arbitrary text independently of any model invocation, so you can run your own vLLM fleet and still call a managed guardrail for content filtering, denied topics, PII detection and contextual grounding checks — over a PrivateLink endpoint, in-Region. That is often a better trade than building the classifier stack yourself.

If policy forbids any managed call, the self-hosted equivalents are Llama Guard and Prompt Guard for classification, NeMo Guardrails for programmable rails, and Presidio for PII. Budget a small GPU for them and put them on the critical path in both directions — a guardrail you only run on input catches half the problem.

A gate, not a dashboard

RELIABILITY

Degrade, do not fail

Multi-AZ node groups; a smaller fallback model on cheaper GPUs when the primary fleet is saturated or capacity is unavailable; circuit breakers around retrieval so a slow vector store cannot exhaust the pool; SQS in front of the batch path to absorb bursts; and per-tenant rate limits so one caller cannot become an outage for everyone.

DISASTER RECOVERY

Region strategy costs real money

Warm-standby in a second Region means paying for idle GPUs; pilot-light means accepting a slow recovery while you fight for capacity. Decide explicitly, write the RTO/RPO down, and remember that a second Region may violate your data-residency SCP — check before you promise it.

Cost engineering

Self-hosting is cheaper per token and more expensive per organisation. Both statements are true, and the crossover is a utilisation number you can calculate before you commit.

The break-even that decides the whole strategy

Take a node at an assumed committed rate of $6/hour sustaining roughly 1,400 output tokens/second under good batching:

  • At 100 % utilisation: 5.04 M output tokens/hour → about $1.20 per million output tokens.
  • At 30 % utilisation: about $4 per million — the idle GPU is billed either way.
  • At 10 % utilisation: about $12 per million, and you have not paid the humans yet.

Now add the part that never appears on the infrastructure bill. A platform team of three engineers, fully loaded, is on the order of $50k/month — roughly the cost of running eight g6e.12xlarge instances continuously, forever. That is the real break-even: self-hosting wins when your token volume is large enough that the per-token saving exceeds the cost of the team, and loses when it is not. Most organisations discover they are on the wrong side of that line about six months in.

Levers, in the order they pay

  1. Batch harder. Raising --max-num-seqs until you hit your TTFT SLO is free throughput. This is usually the single biggest win and it costs nothing.
  2. Quantise. INT4 AWQ or FP8 cuts weight memory 2–4×, which often means a smaller node class, not just headroom.
  3. Route by difficulty. Most traffic does not need the 70B. Classify intent cheaply and send the easy 70 % to an 8B model on a g6. This routinely halves the bill.
  4. Cache semantically. A tenant-scoped vector cache in MemoryDB serves repeated questions for a fraction of a cent and zero GPU seconds. Hit rates of 20–40 % are common in support workloads.
  5. Commit. Compute Savings Plans on the steady floor, On-Demand or Spot above it. Spot is viable for the async batch path with checkpointing, and reckless for interactive serving.
  6. Consider Inferentia. Meaningfully cheaper per token at steady load — conditional on your model compiling cleanly under the Neuron SDK, which you must verify with a proof of concept rather than a datasheet.
  7. Right-size the endpoints. Interface endpoints bill hourly per AZ plus per GB. Twelve endpoints across three AZs is a few hundred dollars a month; the same twelve replicated across twenty VPCs is not. Centralise them in the network account and share via Route 53 Resolver rules and Transit Gateway.

The free one people miss

S3 gateway endpoints cost nothing and process no per-GB charge. S3 interface endpoints bill hourly and per gigabyte. If you are pulling terabytes of model weights and corpus through an interface endpoint because someone created it for on-premises access, you are paying data-processing charges for traffic a gateway endpoint would carry for free. Use both: gateway for in-VPC traffic, interface only for the on-premises and cross-Region paths that genuinely need it.

Quiet privacy leaks

A list of things that are true, that engineers reliably get wrong, and that turn a sealed architecture back into a leaky one without changing a single line of the network diagram.

MYTH 01

“Self-hosted means private.”

It means the weights are private. The prompts still travel wherever your telemetry, tracing, error-reporting and analytics SDKs send them. Audit the egress of your observability stack before you audit anything else — it is the single most common leak in real deployments.

MYTH 02

“Bedrock trains on our data.”

It does not. Inputs and outputs are not used to train the base models, are not shared with model providers, and are processed in the Region you call. Plenty of teams have taken on the entire cost and risk of a GPU fleet to solve a problem that did not exist — and then leaked through an unpinned package index.

MYTH 03

“Our VPC has no internet access.”

Check again. EKS add-ons, the cluster autoscaler, Helm charts, the CNI, cert-manager and half the operator ecosystem pull from public registries by default. If any of them works, something has a route out. Mirror every dependency into ECR and CodeArtifact.

MYTH 04

“We only send anonymised text.”

Embeddings are not anonymised. Embedding-inversion research recovers substantial source text from vectors alone. Treat an embedding with exactly the classification of the document it came from — including in backups and in any “just the vectors” export.

MYTH 05

“The frontend is out of scope.”

Session-replay and product-analytics scripts capture DOM content, which includes the textarea the user typed the confidential question into and the answer rendered beside it. A perfect backend behind a page running third-party JavaScript is not a private system.

MYTH 06

“We pull the model at startup.”

from_pretrained("meta-llama/...") in a container entrypoint is a runtime dependency on a third party, an unpinned artefact, an availability risk, and a token sitting in an environment variable. Mirror weights to S3, verify checksums, and use safetensors so a malicious checkpoint cannot execute code on load.

MYTH 07

“LLM-as-judge is internal tooling.”

Your eval harness sends your golden set — carefully curated, maximally representative real customer data — to whichever judge model it is configured with. If that is an external API, you have built a high-quality export pipeline for your most sensitive corpus. Judge with your own model.

MYTH 08

“Managed vector databases are fine.”

A SaaS vector database outside your accounts holds your entire corpus in a form that is trivially searchable and, per Myth 04, substantially recoverable. If the requirement is zero third-party access, the vector store has to be in your VPC too.

MYTH 09

“It is encrypted, so it is safe.”

Encryption at rest with an AWS-managed key protects against disk theft, not against an over-broad IAM policy — the service decrypts transparently for any principal allowed to read. Customer-managed keys with restrictive key policies are what turn encryption into an access control.

MYTH 10

“Open weights means we can use them.”

Licences differ sharply. Some are permissive, some carry acceptable-use policies and attribution or naming requirements, some restrict commercial use above a user threshold, and some are research-only. Get the licence reviewed before it is embedded in a product roadmap, not after.

A  ·  Architecture & topology8
Walk me through how you would deploy a private LLM on AWS so that no data is shared with anyone.

Start by defining “private” testably: content is processed only by compute we own, never used for third-party training, never leaves a named Region, and all three are provable from logs. Then build in layers. A multi-account landing zone with SCPs that deny unapproved Regions and deny creating any internet gateway or NAT gateway. A workload VPC with private, inference, data and endpoint subnet tiers and no default route — corporate users reach an internal ALB over Direct Connect. Model serving on EKS with vLLM on g6e GPU nodes, weights mirrored to S3 as safetensors and pulled through a gateway endpoint. Retrieval from Aurora with pgvector using row-level security bound to the JWT tenant claim, with embeddings computed by a self-hosted bge-m3. Guardrails on input and output. Every AWS API call exits through interface VPC endpoints whose policies pin aws:PrincipalOrgID. Observability is self-hosted Langfuse writing hashes rather than raw prompts. Evidence is an organization CloudTrail plus all-traffic VPC Flow Logs in a separate log-archive account with Object Lock. Finally, the proof: an Athena query over flow logs showing zero non-RFC1918 egress, run nightly.

Bedrock or self-hosting on EKS — how do you actually decide, and what is the honest privacy difference?

Three questions decide it. Does Legal accept a contractual and architectural boundary rather than a physical one? Do we need specific open weights, custom kernels, or per-tenant LoRA hot-swap? And can we keep GPUs above roughly 35–40 % sustained utilisation? Bedrock wins on total cost below that utilisation line, on time-to-market, and on not needing a platform team. Its privacy position is genuinely strong: in-Region processing, no storage or use of inputs and outputs to train base models, and a VPC interface endpoint so traffic stays on the AWS backbone. Self-hosting gives something different in kind — a boundary I can inspect, where I control the route table and every process. The honest difference is inspectability, not leakage. Many teams choose self-hosting for procurement reasons and then leak more through an unpinned pip index or a SaaS tracing SDK than Bedrock would ever have seen.

What does SageMaker’s EnableNetworkIsolation actually do, and what breaks when you enable it?

It removes network access from the model container entirely — no inbound, no outbound, not even to AWS services. The container cannot download weights at runtime, cannot call S3, cannot reach a licence server and cannot emit telemetry directly. That is exactly what you want for a sensitive inference container, and it means everything the container needs must be baked into the image or delivered by SageMaker itself from the ModelDataUrl before the container starts. Note it is orthogonal to VPC configuration: VPC mode attaches ENIs into your subnets so the platform can reach your resources, whereas network isolation cuts the container off. For maximum isolation you use both, and you accept that you now own the packaging problem.

When would you choose GovCloud, an Outpost, or Snowball Edge over a commercial Region?

Only when a legal or physical constraint makes a commercial Region impossible, because all three cost far more and constrain you severely. GovCloud when the workload is subject to US federal requirements like ITAR or a FedRAMP High boundary; the Secret and Top Secret Regions when the data is classified. Outposts when data-residency law requires the data to stay in a country with no AWS Region, or when a factory or hospital needs inference to survive a WAN outage. Snowball Edge with a GPU for genuinely disconnected environments — a ship, a remote site. The tradeoffs are brutal: a much smaller service catalogue, limited and fixed accelerator capacity, no elastic scaling, and slower feature availability. Verify that every service in your design exists in the target environment before committing, because many do not.

Why separate AWS accounts rather than just separate VPCs?

An account is the strongest blast-radius and quota boundary AWS offers. IAM is account-scoped, so a compromised or over-broad role in one account has no reach into another without an explicit trust relationship. Service quotas are per-account, so a runaway dev workload cannot exhaust the production GPU quota. Billing is naturally attributed. Crucially, SCPs apply per organizational unit, which lets me give the production workload OU a strictly tighter guardrail than dev, and it lets the log-archive account hold evidence that the audited accounts genuinely cannot modify. VPC separation alone gives you network isolation but shares the IAM and quota blast radius, which is the part that actually fails.

Trap  “The model runs on our own GPUs in our own VPC, so our data is private.” What is wrong with that?

It conflates weight hosting with data containment. The weights are private; the content is not, if any of the normal defaults are still in place. A typical stack downloads weights from Hugging Face at boot, runs pip install from public PyPI, ships traces containing full prompts to a SaaS observability vendor, calls a hosted embedding API for the entire corpus during backfill, and resolves arbitrary DNS. Any one of those is a bigger leak than a managed inference API would have been, because the embedding backfill in particular sends everything at once. The right framing is that privacy is an egress property, not a hosting property: for every component, ask what DNS names it can resolve and what IP addresses it can reach. If the answer is “anything”, the workload is not private.

You need to serve five different models. How do you avoid five times the GPU cost?

First, separate the cases. If they are the same base model with different domain adaptations, use LoRA adapters and vLLM’s multi-LoRA serving — one set of base weights in VRAM, adapters swapped per request, near-zero marginal memory. If they are genuinely different architectures, do not co-locate them on one replica; instead route by difficulty so the expensive model only sees traffic that needs it, classify intent with a small cheap model, and put the low-volume models on a shared node with time-slicing or MIG partitioning. For anything with no latency SLO, move it to the async SQS path where you can batch aggressively and use Spot. A SageMaker multi-model endpoint or Triton with model ensembles is the managed version of the same idea.

Design the asynchronous path and explain why it must be separate from the interactive one.

S3 landing prefix → EventBridge → SQS with a dead-letter queue → a worker deployment on GPU nodes → results written back to a KMS-encrypted S3 prefix, with job state in DynamoDB. It must be separate because the two workloads want opposite things. Interactive traffic optimises TTFT, needs a warm floor of replicas and cannot tolerate preemption. Batch traffic optimises throughput per dollar, wants the largest possible batch size, tolerates minutes of latency and can checkpoint through a Spot interruption. Mixing them means the batch job’s long prefills sit in front of a user’s request in the same queue and destroy your p95. Separate node groups, separate queues, separate autoscaling policies — and the batch path is where GPU utilisation above 80 % is actually achievable.

B  ·  Networking & zero-egress8
Enumerate the VPC endpoints this architecture needs, and say why each is there.

Gateway endpoints (free, route-table based): s3 and dynamodb. Interface endpoints (PrivateLink ENIs): ecr.api and ecr.dkr for image pulls, plus s3 as an interface endpoint if on-premises callers need it; sts for AssumeRole; kms for envelope decryption; logs and monitoring for CloudWatch; secretsmanager for database credentials; ssm, ssmmessages and ec2messages for Session Manager access without a bastion; eks and eks-auth for the cluster API; elasticloadbalancing and ec2 for the AWS Load Balancer Controller and Karpenter; autoscaling if you use managed node groups; sqs and events for the async path; bedrock-runtime if you use Bedrock Guardrails or a hybrid model path; sagemaker.api and sagemaker.runtime if you use SageMaker. Enable private DNS on all of them so unmodified SDK calls resolve to the ENI. The discipline is to add none you cannot justify — each one is another door.

Gateway endpoint or interface endpoint — what is the difference and when does each apply?

A gateway endpoint is a route-table entry for S3 or DynamoDB. It costs nothing, has no per-gigabyte charge and no ENI, but it only works for traffic originating inside the VPC — it is invisible to on-premises networks arriving over Direct Connect or a peered VPC. An interface endpoint is a real ENI with a private IP in your subnet, backed by PrivateLink. It bills per endpoint per AZ per hour plus per gigabyte processed, supports endpoint policies and security groups, and is reachable from on-premises and across peering. The correct pattern for S3 is both: gateway for the high-volume in-VPC traffic like pulling 140 GB of weights, interface only for the specific on-premises or cross-account paths that need it.

An attacker has valid credentials inside your VPC. How do you stop them copying the corpus into their own S3 bucket?

The IAM policy alone will not save you, because the credentials are valid. Two controls do. First, a VPC endpoint policy on the S3 endpoint that allows actions only against your named bucket ARNs and only when aws:PrincipalOrgID matches your organization — a PutObject to an external bucket is denied at the endpoint before IAM is consulted. Second, the mirror-image bucket policy that denies all access unless aws:SourceVpce equals your endpoint ID, so the same credentials stolen and used from a laptop return AccessDenied. Add Route 53 DNS Firewall so the attacker cannot resolve an arbitrary hostname to try a different channel, and VPC Flow Logs so the attempt is visible. Belt, braces, and a camera.

Explain DNS exfiltration in this context and how you prevent it.

Even with no IP route to the internet, a process can encode data into subdomain labels — base32chunk1.exfil.attacker.com — and issue lookups. The recursive resolver dutifully forwards the query toward the authoritative server, whose query log now contains the data. No TCP connection to the internet ever occurred, so a firewall watching for outbound sessions sees nothing. The fix is Route 53 Resolver DNS Firewall with an allow-list rule group for the handful of domains you actually need, followed by a lowest-priority BLOCK rule on *. Log the blocked queries — a burst of NXDOMAIN attempts to a single parent domain is one of the clearest compromise signals you will ever get.

SCP, IAM policy, permission boundary, endpoint policy, resource policy — how do they interact?

An action is allowed only if every applicable layer allows it, and any explicit Deny anywhere wins. Evaluation order in effect: the SCP defines the maximum possible permissions for the whole account and cannot be escaped by any principal including the root user; the permission boundary caps what an individual role can be granted; the identity policy grants; the resource policy (bucket policy, KMS key policy) grants or denies independently; the session policy narrows further; and the VPC endpoint policy filters requests arriving through that endpoint. The practical consequence for this design is that SCPs and endpoint policies are the only two layers a compromised account administrator cannot rewrite, which is why the zero-egress guarantee is built out of those two and not out of IAM.

How do corporate users reach the service if there is no public endpoint?

Direct Connect for the primary path with a Site-to-Site VPN as encrypted backup, both landing on a Transit Gateway in the network account, with route propagation to the workload VPC. An internal ALB with a private-only scheme fronts the service; its DNS name lives in a Route 53 private hosted zone associated with the VPC and resolvable from on-premises via Resolver inbound endpoints, so the corporate name resolves to a private IP. For remote staff, AWS Client VPN or the existing corporate VPN. If other business units in other accounts need access, expose the service through PrivateLink as a provider using an NLB — consumers get an endpoint in their own VPC and never see your CIDR, which is cleaner than peering and does not create transitive routing.

Trap  Your VPC endpoint bill is $12,000 a month. Diagnose it.

Almost certainly two mistakes compounding. First, endpoint sprawl: interface endpoints bill per endpoint per availability zone per hour. Roughly twelve endpoints across three AZs is a few hundred dollars a month — fine. Replicate that in twenty VPCs across twenty accounts and you are at $5,000–6,000 in hourly charges alone before any traffic. The fix is to centralise endpoints in the network account and share them through Transit Gateway plus Route 53 Resolver forwarding rules. Second, data processing on the wrong endpoint type: if bulk S3 traffic — model weights, corpus backfill, log delivery — is routed through an interface endpoint, you pay per gigabyte for traffic a free gateway endpoint would carry at no charge. Check the route tables. The naive answer is “delete some endpoints”, which breaks the workload; the right answer is centralise and re-route.

On EKS, why are security groups not sufficient, and what do you add?

A security group attaches to an ENI. With the standard VPC CNI, pods share the node’s ENIs, so a security group is effectively a node-level control — every pod on that node gets the same network permissions, which destroys the distinction between your orchestrator pod and your model pod. Two fixes, and you generally want both: security groups for pods, which assigns branch ENIs so a pod gets its own security group, and Kubernetes NetworkPolicy enforced by the VPC CNI’s policy engine or Calico, which gives you pod-selector-based rules including egress. Layer them: NetworkPolicy for intra-cluster intent, security groups for the VPC-level boundary. And remember NetworkPolicy is default-allow until the first policy selects a pod, at which point it becomes default-deny for that direction — a fact that has caused many confusing outages.

C  ·  Security, IAM, encryption, compliance8
Why insist on customer-managed KMS keys when AWS-managed keys use the same algorithm?

The cryptography is identical — AES-256 either way. What differs is control and evidence. A customer-managed key has a key policy you author, so you can restrict Decrypt to specific roles, add conditions such as kms:ViaService or a source VPC endpoint, and require MFA for administrative actions. You see every Decrypt call in CloudTrail with the calling principal, which turns the key into an audit trail of data access. You can rotate on your own schedule, and critically you can disable it — which instantly renders every copy and every backup of that data unreadable, including copies you have lost track of. With an AWS-managed key you have none of that; the service decrypts transparently for any principal with read permission. Customer-managed keys are what turn encryption from a storage property into an access control.

What does the Nitro System actually guarantee, and do Nitro Enclaves help for LLM inference?

Nitro moves virtualisation into dedicated hardware and removes interactive access to the host: there is no SSH into the hypervisor, no mechanism for an AWS operator to read guest memory, and the design has been independently reviewed. That is a meaningful baseline for every EC2 instance. Nitro Enclaves add an isolated compute environment carved from the parent instance with no persistent storage, no interactive access and no external network, plus cryptographic attestation — KMS can be configured to release a key only to an enclave whose measured image hash matches the key policy. That is excellent for key custody, tokenisation and small sensitive computations. It is a weaker fit for LLM inference specifically, because enclaves have not historically had GPU access. The pragmatic pattern is to hold keys and perform decryption inside an enclave while relying on the Nitro System’s guarantees for the GPU instance itself. If you need GPU-level confidential computing, that is an H100/H200 Confidential Computing question and you should verify current support rather than assume it.

Users can upload documents that get indexed. How do you handle prompt injection?

Accept up front that there is no complete fix, and design for containment rather than prevention. Structurally separate instructions from data — retrieved content goes in a clearly delimited context block and the system prompt states that content there is data, never instruction. Run a classifier such as Prompt Guard or Bedrock Guardrails on both the user turn and the retrieved chunks. Strip or escape markup, hidden text, zero-width characters and white-on-white content at ingest. Then contain the damage: tools get an explicit allow-list, each with its own minimal IAM role rather than the orchestrator’s, anything that writes or sends requires human approval, tool results are re-screened as untrusted input, and loop iterations and total tokens are hard-capped. The test of the design is not “can it be injected” — it can — but “what is the worst thing a successful injection can cause”.

Describe your IAM model for the workloads.

No long-lived access keys anywhere. Pods get identity through EKS Pod Identity (or IRSA), so each service account maps to a role scoped to exactly its resources — the retriever role can read one Secrets Manager secret and decrypt with one key; the vLLM role can read the weights prefix and nothing else; each agent tool has its own role. Permission boundaries are attached so that even a role created by a mistaken Terraform change cannot exceed the guardrail. CI authenticates by OIDC federation from GitHub with a trust policy conditioned on the specific repository and branch, so a fork cannot assume it. Human access is through IAM Identity Center with short sessions and no standing production write access — elevation goes through an approval workflow. IMDSv2 is required with a hop limit of 1 so a compromised container cannot reach the node role. IAM Access Analyzer runs continuously for external-access and unused-access findings, and unused permissions get removed on a schedule.

How do you stop your own platform engineers from reading user prompts?

This is the control most designs are missing, and the one auditors test. Start by not creating the exposure: audit records store a SHA-256 of the prompt, token counts, tenant, latency and guardrail verdicts — not the text. Full-fidelity capture exists but is off by default and gated behind a separate, explicitly named debug mode. The trace store uses its own KMS key whose policy grants Decrypt only to a break-glass role; assuming that role requires an approved change record, is time-boxed by a session policy, and raises an EventBridge alarm to the security team every single time. CloudWatch Logs groups are encrypted with the same key so an engineer with generic log-read permission still cannot decrypt. Then close the side channels: no core dumps to shared storage, redaction at the emitter rather than at the sink, and a policy that support-case attachments are scrubbed. Privacy from third parties is the easy half.

Which of the OWASP LLM risks does self-hosting not fix?

Almost all of them. Self-hosting addresses only the subset concerned with a third party seeing your data. Prompt injection (LLM01) is untouched — it is an application-design problem. Sensitive information disclosure (LLM02) gets worse if you fine-tune on customer data, because the model memorises. Supply chain (LLM03) gets substantially worse, because you now own weight provenance, pickle deserialisation risk and a large Python dependency tree. Data poisoning (LLM04), improper output handling (LLM05), excessive agency (LLM06), system prompt leakage (LLM07), vector weaknesses (LLM08) and misinformation (LLM09) are all unchanged. Unbounded consumption (LLM10) changes shape: instead of a surprise invoice you get a saturated GPU fleet and an outage. The interviewer is checking whether you think hosting is a security control. It is a data-residency control.

A user exercises their GDPR right to erasure. What has to happen?

Enumerate every place a derivative of that document can exist, because deleting the S3 object is the easy 10 %. You must delete: the source object and all its versions (versioning means a delete marker is not a deletion), every chunk row and its vector in the vector store, any entries in the semantic cache whose value was derived from it, trace and audit records containing the content, any search index or keyword index entry, and backups and snapshots — which is why point-in-time backup retention needs to be a deliberate, documented number. If the document was in a fine-tuning dataset, prompting cannot remove it and you are looking at retraining or discarding the adapter. The design consequence is to build the deletion path on day one with a deletion-request queue, a per-document lineage record from ingest, and a verification job that confirms zero residual matches. Retrofitting this is far harder than building it.

Trap  “We strip PII with a regex before embedding, so the vector store is safe.” Critique that.

Three problems. First, regex PII detection has poor recall on unstructured text — names, addresses in unusual formats, indirect identifiers and free-text clinical notes all slip through; a trained model such as Comprehend or Presidio does better and still is not perfect. Second, and more fundamentally, removing PII does not make the remainder non-sensitive. “The patient’s biopsy showed stage 3” with the name removed is still confidential, and combined with a timestamp and a department it is frequently re-identifiable. Third, embeddings are not anonymised: embedding-inversion techniques recover substantial source text from vectors alone, so the vector store must be classified and protected exactly like the source documents. Redaction is a useful defence-in-depth layer for what gets logged and displayed. It is not a mechanism for downgrading the classification of your corpus, and treating it as one is how teams justify putting embeddings somewhere they should not be.

D  ·  GPU & inference performance8
Size the GPU fleet for a 70B model, 8k context, 40 concurrent streams. Show your working.

Three consumers of VRAM. Weights: at INT4 AWQ roughly 0.53 bytes per parameter including scales, so about 37 GiB; at BF16 it would be 140 GiB. KV cache: 2 × n_layers × n_kv_heads × head_dim × dtype_bytes per token. For a 70B with 80 layers, 8 KV heads under GQA and head dimension 128 at FP16, that is 2 × 80 × 8 × 128 × 2 = 327,680 bytes, or 320 KiB per token — 2.5 GiB for a full 8k sequence, so 100 GiB for 40 of them. Overhead: activations, CUDA graphs and allocator fragmentation, call it 10 GiB. Total roughly 147 GiB, which fits a g6e.12xlarge at 4×L40S = 192 GiB with tensor parallelism of 4. For AZ redundancy I would run two such nodes, each sized for full peak, plus a small g6 for the embedding and reranker models. The point I would emphasise is that the KV cache is two thirds of the requirement — so --max-model-len and --max-num-seqs are capacity decisions, and doubling the context window changes the hardware, not just a config file.

Your TTFT is 4 seconds and users are complaining. Walk me through the diagnosis.

TTFT is prefill plus queueing, so I split those first. Check vllm:num_requests_waiting — if the queue is deep, this is a capacity or admission-control problem, not a model problem, and I scale out or shed load. If the queue is empty, prefill itself is slow, so I look at prompt length: a RAG prompt that has grown to 20k tokens because someone raised top-k from 5 to 50 will do exactly this, and the fix is reranking down to 8 chunks rather than stuffing the window. Then I check whether prefix caching is enabled and whether it is actually hitting — a long shared system prompt should be nearly free on a cache hit, and hit rate collapses if the load balancer scatters requests across replicas, so consistent-hash routing may be the fix. Then chunked prefill, so one enormous prompt cannot block the batch. Then the obvious ones: cold replica still loading weights, CPU-bound tokenisation, a slow retrieval call being counted inside my TTFT measurement, or an ALB idle-timeout interacting badly with streaming. The mistake to avoid is buying a bigger GPU: prefill is compute-bound and a 20k-token prompt is expensive on any hardware.

Explain continuous batching and why it changes the economics so much.

Static batching collects N requests, pads them to the longest sequence, runs them together and returns when the slowest finishes. Every shorter sequence wastes compute on padding, and no new request can join until the whole batch completes — so the GPU idles between batches and tail latency is set by the worst request. Continuous (or in-flight) batching operates at the iteration level: after every forward pass the scheduler evicts finished sequences and admits waiting ones, so the batch is continuously refilled and there is no padding waste. Combined with PagedAttention — which allocates KV cache in fixed-size blocks like virtual memory pages, so no contiguous reservation and almost no fragmentation — it typically yields an order of magnitude more throughput on identical hardware than a naive loop. This is why the choice of inference server matters more than the choice of GPU for most deployments, and why “we wrote our own serving layer” is usually a large, invisible cost.

Tensor, pipeline and data parallelism — when do you reach for each?

Tensor parallelism splits individual weight matrices across GPUs, so every GPU participates in every layer. It needs high-bandwidth interconnect because there is an all-reduce per layer, so keep it inside a single node — NVLink on p5, or PCIe on g6e where TP=4 is fine and TP=8 across two nodes is not. Use it when the model does not fit on one GPU; it also reduces latency because the work is genuinely divided. Pipeline parallelism splits by layer across GPUs or nodes, so it tolerates slower interconnect, but it introduces bubbles and does not improve single-request latency. Use it when the model will not fit within one node even with TP. Data parallelism is just independent replicas behind a load balancer — it multiplies throughput, does nothing for a model that does not fit, and is what you should reach for first if the model does fit. The practical answer for a quantised 70B is TP inside the node, data parallelism across nodes, and no pipeline parallelism at all. For MoE models add expert parallelism, distributing experts across devices.

Compare the quantisation options. What does weight quantisation not fix?

BF16/FP16 is the baseline at 2 bytes per parameter. FP8 halves that with minimal quality loss but needs Hopper-class hardware or newer for native support. INT8 SmoothQuant is a reasonable middle ground. INT4 AWQ and GPTQ get to roughly 0.5 bytes per parameter with typically small quality degradation on most tasks — AWQ tends to preserve quality slightly better in my experience because it protects salient weight channels — but both degrade more noticeably on hard reasoning and long-context tasks, so you must measure on your own eval set rather than trusting a benchmark table. GGUF is for CPU and llama.cpp deployments. The critical thing weight quantisation does not fix is the KV cache: that is set separately, and on a high-concurrency long-context workload the KV cache is the larger consumer. Going BF16 to INT4 on a 70B saves about 103 GiB of weights and zero bytes of KV cache — you need an explicit FP8 KV-cache setting for that.

Trap  GPU utilisation reads 95 % but throughput is poor. What is going on?

“GPU utilisation” as reported by nvidia-smi only means at least one kernel was resident during the sampling window — it says nothing about how much of the device’s capability is being used. LLM decoding is memory-bandwidth-bound: each token requires reading the entire weight set from HBM to do a small amount of arithmetic, so a batch size of 1 pins “utilisation” near 100 % while achieving a tiny fraction of peak FLOPs. The diagnostic metrics are SM occupancy and achieved memory bandwidth from DCGM, plus the server’s own running batch size. The fix is almost always to batch more: raise --max-num-seqs until TTFT approaches your SLO, enable chunked prefill so prefill and decode interleave, and check that requests are not being serialised by a load balancer holding connections. The wrong response — and the one the question is fishing for — is to add GPUs, which will show 95 % utilisation too.

Adding a GPU replica takes 14 minutes. Get it under three.

Break the 14 minutes into its parts and attack each. Instance launch and GPU driver plus device-plugin readiness is typically 2–4 minutes — use an EKS accelerated AMI with drivers pre-installed rather than installing at boot, and pre-warm capacity with Karpenter so a node is already joining before you need it. Container image pull of a 10–15 GB CUDA image is often the biggest slice — bake the image into a custom AMI, or enable SOCI lazy loading on ECR so the container starts before the whole image lands, and never bundle weights into the image so a code deploy does not re-pull them. Weight loading of 37–140 GB is the other big slice — FSx for Lustre linked to the weights bucket gives parallel multi-GB/s reads, Mountpoint-S3 is simpler and often sufficient, and a pre-warmed EBS snapshot is the blunt instrument. Then stop needing it to be fast: hold a warm floor of one replica per AZ, scale on queue depth before saturation rather than after, and route overflow to the async queue so no user waits for a node.

What metric do you autoscale GPU inference on, and why not GPU utilisation?

Queue depth and latency against SLO — specifically vllm:num_requests_waiting and observed TTFT — surfaced to KEDA or the Kubernetes Gateway API inference extension, with Karpenter provisioning the nodes. GPU utilisation is a bad signal for the reason above: it saturates long before the server is actually busy, so it both triggers late and never scales down. Requests-per-second is also poor because LLM requests are wildly heterogeneous — a 200-token prompt and a 20,000-token prompt are not comparable units of work. Queue depth is the honest measure of unserved demand. I would set the scale-up threshold well below saturation because provisioning takes minutes, use a long stabilisation window on scale-down to avoid thrashing expensive nodes, define a NodePool with a cheaper fallback instance family at lower weight in case the preferred family has no capacity, and keep a minimum warm replica count per AZ rather than scaling to zero for interactive traffic.

E  ·  RAG & the data plane8
Design the document ingestion pipeline.

S3 landing prefix with versioning and a customer-managed key → EventBridge on object-created → Step Functions as the orchestrator, because you need retries, partial failure handling and visibility across a multi-stage job. Stages: parse (Textract for scanned PDFs and forms, an in-VPC parser for native documents, preserving structure — headings, tables, page numbers); classify and redact (Comprehend PII detection, with Macie discovering what is in the bucket at rest); chunk; embed on a self-hosted model; upsert into the vector store with tenant, classification, source system, source ACL and document version as metadata; write a lineage record so deletion and re-embedding are tractable. Idempotency keyed on content hash so a redelivery does not duplicate chunks, a dead-letter queue for poison documents, and the whole thing runs in private subnets with no egress. The two rules that matter: the chunk carries its own access-control metadata copied at index time, and the index is versioned so you can deploy a new embedding model blue/green.

Pick a vector store on AWS and defend the choice.

For most enterprise RAG I would start with Aurora PostgreSQL and pgvector, for a reason that is about security rather than search: PostgreSQL row-level security lets me bind tenant filtering to a session variable set from the verified JWT claim, so isolation is enforced by the database and cannot be forgotten by an application code path. I also get transactions, joins to the relational metadata I already have, familiar operations, and a single system to back up. I would move to OpenSearch when lexical search quality genuinely matters — it has real BM25, native hybrid search with reciprocal rank fusion, and scales past the point where HNSW index maintenance in Postgres becomes painful, at the cost of needing real cluster-sizing skill. MemoryDB for the semantic cache, because that is a latency problem not a storage problem. S3 Vectors for very large cold corpora where the latency budget is generous. What I would not do is put the corpus in a SaaS vector database, because that reintroduces exactly the third-party access the whole architecture exists to prevent.

How do you guarantee one tenant cannot retrieve another’s documents, and how do you prove it?

Enforce it where it cannot be bypassed, not in application code. With pgvector, PostgreSQL row-level security policies on the chunks table keyed to a session variable that the connection layer sets from the verified JWT claim — every query is filtered by the database whether or not the developer remembered a WHERE clause. With OpenSearch, a separate index per tenant plus an IAM or fine-grained access policy so only that tenant’s role can read it. Never derive the tenant from anything the client sends in the request body. Then the proof: an automated test in CI that authenticates as tenant A, issues queries deliberately engineered to be semantically closest to tenant B’s documents, and fails the build if a single B-owned chunk appears in the candidate set — asserted before reranking, because the reranker is a relevance component and not a security control. Also check the semantic cache, which is the most commonly missed leak: an unkeyed cache will happily serve tenant A’s answer to tenant B.

Why can you not just use a hosted embedding API?

Because it inverts the threat model you built everything else to satisfy. Chat traffic is a trickle; the embedding backfill is the whole corpus, sent in bulk, at the start. If the requirement is that no third party processes your content, an external embedding call violates it more comprehensively than anything else in the stack. The good news is that this is the cheapest constraint to satisfy: strong open embedding models — bge-m3, E5, Nomic Embed, Qwen3-Embedding — run comfortably on a single g6, batch extremely well, and are usually competitive with hosted options on retrieval benchmarks. The same argument applies to the reranker: a cross-encoder such as bge-reranker-v2-m3 over the top 50 candidates typically improves answer quality more than upgrading the generation model, and a managed reranker sees every document you send it.

You need to upgrade the embedding model. What happens to your 80 million existing vectors?

They are all invalid. Vectors from different embedding models are not comparable, and dimensionality often differs too, so this is a full re-index rather than a migration. The plan: build a new versioned index alongside the live one, re-embed the corpus as a batch job on the async path (Spot instances with checkpointing, since there is no latency SLO), and run both indexes in parallel while you evaluate. Shadow production queries against both and compare retrieval metrics on your golden set — recall@k and MRR — before cutting over, because a newer model with better benchmark scores can be worse on your domain. Cut over behind a feature flag with instant rollback, keep the old index for a defined window, then delete it. This is precisely why the index must be versioned and the pipeline re-runnable from day one; teams that index once and treat it as permanent discover this at the worst possible moment.

Why bother with hybrid search and reranking instead of pure vector similarity?

Because dense retrieval and lexical retrieval fail in different, complementary ways. Embeddings capture semantics but are weak on exact tokens — part numbers, error codes, proper nouns, statute references, rare acronyms — where BM25 is excellent, and BM25 is blind to paraphrase where embeddings shine. Fuse both candidate lists with reciprocal rank fusion and recall improves materially at essentially no latency cost. Then reranking does something different again: retrieval optimises for recall over a large candidate set, and a cross-encoder that jointly attends to query and document is far more accurate at ordering than any bi-encoder similarity score. Retrieve 50 cheaply, rerank to 8 accurately, and send only those 8 to the model. That last step also cuts your prefill cost dramatically, which improves TTFT — so it pays for itself twice.

What actually matters about chunking?

Preserving enough context that a chunk is interpretable on its own, and preserving structure so citations are usable. Fixed-size character splitting is the worst common choice because it cuts mid-sentence and mid-table. Recursive splitting on document structure — headings, then paragraphs, then sentences — with a modest overlap is a solid default. Beyond that, two techniques earn their complexity: contextual retrieval, where you prepend a short model-generated summary of the parent document to each chunk before embedding, which substantially improves retrieval on chunks full of pronouns and references; and keeping a small chunk for matching, larger parent for generation, so you retrieve precisely but give the model enough surrounding text to reason with. Always carry metadata: source URI, page or section, version, tenant, classification. And do not treat chunk size as a global constant — tables, code and prose want different handling, and a pipeline that recognises document type will beat one that does not.

Trap  Retrieval metrics look good but the answers are wrong. Where do you look?

Resist the urge to change the model, which is the reflex answer. Decompose the pipeline and measure the stages separately. First confirm the correct chunk is actually in the final prompt — good recall@50 with a reranker that drops the right chunk at position 9 when you send 8 is a very common failure, and it shows up as good retrieval metrics and bad answers. Then check prompt assembly: chunk order matters, models attend less to the middle of a long context, and a bloated context can bury the answer — sending fewer, better chunks often fixes it outright. Then check for conflicting sources, because two contradictory documents in context produce confident nonsense; that is a data-freshness and de-duplication problem, not a model problem. Then look for the answer requiring synthesis across more chunks than you retrieve, or aggregation the retriever fundamentally cannot do (“how many contracts expire this quarter” is a SQL question wearing a RAG costume). Only after all of that is it worth touching the generation model or the prompt.

F  ·  Cost, reliability & operations8
Show me the break-even calculation between self-hosting and a managed API.

Take a node at a committed rate — assume $6 per hour for a 4×L40S box — sustaining roughly 1,400 output tokens per second under good batching. That is 5.04 million output tokens per hour, so about $1.20 per million output tokens at 100 % utilisation. At 30 % utilisation it is about $4 per million, because you pay for the idle accelerator either way. At 10 % it is about $12. Compare that to the managed per-token price for the model class you need. Then add the cost nobody puts in the spreadsheet: a platform team of three engineers fully loaded is on the order of $50,000 a month, which is roughly eight of those nodes running continuously, forever. So the real break-even is volume high enough that the per-token saving exceeds the cost of the team. Below that, self-hosting is more expensive and slower to ship. I would also stress that all these numbers must be re-derived against current pricing in the target Region — GPU pricing moves.

How do you roll out a new model version safely?

Treat the model as a versioned artefact, not a configuration change. It enters a registry with its evaluation results attached and cannot be promoted without passing the gate. Then a staged rollout: shadow first, mirroring real production traffic to the new version without serving its responses, which lets you compare latency, cost and output quality on real distributions with zero user risk. Then a canary at 1–5 % with automatic rollback on error rate, latency SLO breach, guardrail block rate and thumbs-down rate. Then progressive ramp. Keep the previous version warm for the entire window so rollback is a routing change rather than a redeploy — with GPU provisioning times, a rollback that requires new nodes is not a rollback. And version the prompt template together with the model, because a prompt tuned for one model routinely regresses on another; treating them as independently deployable is a reliable source of mysterious quality drops.

What do you monitor, and where does it go?

Three families, deliberately separate. Infrastructure: GPU utilisation, VRAM, SM occupancy, achieved memory bandwidth and temperature via the DCGM exporter into Amazon Managed Prometheus, plus node and pod health. Serving: TTFT and TPOT as distributions not averages, queue depth, running batch size, preemption count, prefix-cache hit rate and KV-cache occupancy. Product: tokens and cost per tenant, retrieval hit rate, guardrail block rate by category, citation coverage, and explicit user feedback. Alert on the serving SLOs, not on utilisation. The privacy-critical part is where it goes: traces go to a self-hosted Langfuse or Phoenix in the VPC, backed by Aurora and an encrypted S3 bucket, with prompt bodies replaced by hashes by default. Sending traces to a SaaS collector is the single most common way a technically sealed architecture leaks, and it is usually done by adding one line to a config file.

How do you evaluate quality in CI without leaking your evaluation set?

The golden set is the most sensitive artefact you own — it is curated, representative real customer data, which is exactly what an exfiltration would target. So the eval harness runs inside the VPC, on the eval account, against your own models, and the judge is your own model rather than an external API. That last point trips people up: the moment you configure an external LLM-as-judge, you have built a high-quality export pipeline for your most sensitive corpus. Structurally: a few hundred domain questions with expected behaviour; retrieval metrics (recall@k, MRR, context precision) reported separately from generation metrics (faithfulness, answer relevance, citation correctness) so you know which half regressed; deterministic checks for format and refusal behaviour; and adversarial suites via garak and PyRIT covering injection, jailbreak and PII extraction. It runs on every model, prompt or retrieval change and blocks the merge on regression. Judge reliability itself needs periodic human spot-checking, or you are trusting a metric nobody has validated.

You planned for p5 instances and AWS has no capacity in your Region. Now what?

This is an operational reality, not a hypothetical, and the answer had better be prepared in advance. Short term: check whether the model fits a quantised deployment on the far more available g6e family — a 70B at INT4 on 4×L40S covers a great many workloads, and this is precisely why quantisation is a capacity strategy and not just a cost one. Medium term: ML Capacity Blocks to reserve GPUs for a defined future window, or On-Demand Capacity Reservations for steady baseline, and raise the accelerator vCPU service quota early because that takes days. Architecturally: define the Karpenter NodePool with multiple instance families and multiple AZs weighted by preference so the scheduler falls back automatically rather than pending forever; keep a smaller fallback model that can absorb traffic in degraded mode; and push everything latency-tolerant onto the async queue. A design that assumes p5 availability and gets none is a design that does not ship.

One tenant’s runaway agent loop is consuming your entire GPU fleet. Fix it now and fix it permanently.

Immediately: rate-limit or block that tenant at the API gateway or WAF, which requires that per-tenant identity already be attached to every request — if it is not, that is the first finding. Permanently, layers: per-tenant token-bucket quotas on requests per minute and tokens per hour enforced at the gateway; a hard cap on agent loop iterations and total tokens per conversation; --max-model-len to bound any single prefill; WAF body-size limits so a 500k-character paste cannot reach a GPU; admission control that queues rather than accepts unbounded concurrency, with a fast 429 and Retry-After when the queue is full; and separate node groups or at minimum priority classes so an interactive tier cannot be starved by a batch tier. Then the observability to see it early: cost and tokens per tenant on a dashboard with anomaly alarms, because the alert should fire before the pager does. This is OWASP LLM10, unbounded consumption, and self-hosting makes it worse than a metered API because the failure mode is an outage instead of an invoice.

Design disaster recovery. What are your RTO and RPO, and what does each option cost?

First check whether multi-Region is even legal — if a data-residency SCP pins you to one Region, cross-Region DR is off the table and you are doing multi-AZ plus a restore plan, which you should say out loud rather than quietly designing something non-compliant. Within a Region, multi-AZ node groups and a Multi-AZ Aurora cluster give you an RTO of minutes for infrastructure failure. For Region loss the honest options are: backup and restore (cheapest, RTO of many hours, and you will be competing for GPU capacity in the recovery Region at exactly the wrong moment); pilot light (data replicated continuously, weights pre-staged in the second Region’s S3, infrastructure defined in Terraform but not running — RTO of an hour or two, cost is storage plus replication); or warm standby (a small live fleet, RTO of minutes, and you pay for idle GPUs). The distinguishing insight is that for LLM workloads the recovery bottleneck is usually accelerator capacity, not data — so if the RTO is genuinely tight, you need a capacity reservation in the second Region, and that is the real line item.

Trap  “We will run inference on Spot instances and save 70 %.” Critique that.

Right instinct, wrong workload. Spot gives a two-minute interruption notice. For interactive inference that is not enough time to be useful: draining a GPU node means finishing in-flight generations, and a replacement replica needs minutes to launch, pull an image and load 37–140 GB of weights — so an interruption is a user-visible outage, not a graceful migration. Worse, large-GPU Spot capacity is exactly the capacity that is scarce, so interruption rates on the instance types you want are high and correlated, meaning you can lose several nodes at once during a demand spike. Where Spot genuinely works is the async batch path: SQS-driven workers with checkpointing, idempotent jobs, no latency SLO, and a re-drive policy — there the savings are real and the interruption is invisible. The mature answer is a Compute Savings Plan on the steady interactive floor, On-Demand above it, and Spot exclusively for batch, fine-tuning and evaluation.

A 90-day build order

The sequence matters more than the components. Build the boundary before you build the product, because retrofitting a boundary around a working system is how privacy programmes fail.

  1. Days 1–10Decide and write down what “private” means

    Get Legal, Security and Engineering to agree the four clauses in §1 and the compliance regimes in scope. Pick the Region. Choose the topology from Fig. 2 — and if the honest answer is Bedrock, take it and stop here. Everything downstream depends on this being written, agreed and specific.

  2. Days 5–20Landing zone and guardrails, before any workload

    Control Tower, the OU structure, the SCPs, the organization CloudTrail into a locked log-archive account, Config conformance packs, GuardDuty and Security Hub. Do this first: it is much harder to impose an SCP on a running workload than to build the workload inside one.

  3. Days 15–30The sealed VPC, proven empty

    Terraform the VPC with no IGW and no NAT, the subnet tiers, the endpoint rack, DNS Firewall with an allow-list, and Direct Connect or VPN connectivity. Then run the Athena flow-log query from §5 and confirm it returns zero rows before anything interesting is deployed. This is your baseline; every later violation is now a diff.

  4. Days 25–40One model, one endpoint, no product

    EKS with a GPU node group, the NVIDIA GPU Operator, vLLM serving one quantised model from an S3 weights mirror. Benchmark TTFT and TPOT honestly against realistic prompt-length distributions. Re-run the flow-log query. Resist all pressure to add features until the numbers and the boundary both hold.

  5. Days 35–55The data plane and tenant isolation

    Ingestion pipeline, self-hosted embeddings, the vector store with database-enforced tenant filtering, hybrid search and a reranker. Write the cross-tenant leakage test first and make it fail, then make it pass. This is the step that decides whether the system is trustworthy.

  6. Days 45–65Guardrails, observability and the eval gate

    Input and output guardrails on the critical path. Self-hosted tracing that logs hashes, with full capture behind a break-glass role. The golden set and the CI gate, judged by your own model. Until the eval gate exists you cannot safely change anything, so this is not a phase-two nicety.

  7. Days 60–80Scale, cost and failure

    Karpenter with a multi-family fallback NodePool, KEDA on queue depth, the async SQS path, per-tenant quotas and cost attribution, semantic caching, and small-model routing. Then break it deliberately: kill an AZ, saturate the fleet, revoke a KMS key, and write the runbooks from what you learn.

  8. Days 75–90Turn controls into evidence

    Automate every query in the §11 evidence table to run nightly and alert on drift. Red-team with garak and PyRIT. Walk an internal auditor through the claim-to-artefact table and fix whatever you cannot demonstrate without your own commentary. That gap, whatever it turns out to be, is the real state of the system.

If you remember one thing

The hardest problems in this architecture are not the GPUs. They are the route table, the tenant filter, and the log line that quietly contains the prompt. Get those three right and the rest is ordinary engineering.
